AI脆弱性診断の競争力は、評価を回し続ける基盤にある

PentestEvalとMetaVulを手がかりに、診断結果の揺らぎを工程ごとに捉え、評価をハーネスの継続的な改善につなぐ基盤について考える。

診断技術・評価脆弱性診断AI for Securityハーネス評価基盤

はじめに：一度発見できたことを、品質と呼べるか

AIを使った脆弱性診断を評価するとき、「脆弱性を発見できた」という結果をどう扱えばよいのでしょうか。

同じ対象に対して診断を繰り返せば、毎回同じ情報を集め、同じ検査を選び、同じ結論に至るとは限りません。ある回では発見できても、別の回では見逃す可能性があります。一度の成功だけで診断品質を判断するのは難しいと思います。

そこで知りたいのは、結果が変わった理由です。情報収集で対象を見落としたのか。対象は把握したが、必要な検査を選ばなかったのか。検査を実施したものの、その結果から脆弱性を判断できなかったのか。

これらはすべて「見逃し」です。しかし、直すべき工程はそれぞれ違います。失敗を一つの数字にまとめてしまうと、ハーネスのどこを改善すべきかが見えなくなります。

診断工程の揺らぎをどう捉えるか

最初に注目したいのは、情報収集です。

診断のたびに把握する画面、API、パラメータ、技術構成が変われば、その後に立てる仮説や選ぶ検査も変わります。初期の小さな差が後続の判断に伝わり、最終的な発見の有無を左右するかもしれません。

同じ情報が得られても、検査の選択は揺れ得ます。なぜその攻撃方法を選び、別の方法を選ばなかったのか。優先順位を付けた結果なのか、対象の特性から不要と判断したのか、それとも検査の必要性に気づかなかったのか。

「何を検査したか」に加えて、「何を検査しなかったか」とその理由が分かれば、未検査による見逃しと、検査後の判定による見逃しを分けられます。複数回の診断結果を比較して初めて、どの工程が不安定なのかを考えられるはずです。

PentestEvalが示す、工程別評価の意味

この問いを考える手がかりになるのが、PentestEvalです。

この研究は、ペネトレーションテストを情報収集、弱点の収集と選別、攻撃判断、攻撃手順の生成と修正という工程に分けます。最終的に攻撃が成功したかだけでなく、途中のどの判断や実行に課題があるかを測ろうとしています。

特に興味深いのは、中間工程の出力を専門家が用意した正解に置き換える実験です。論文のパイプラインでは、弱点の収集、選別、攻撃判断に正解を与えていくと、最終的な成功率も上がりました。これは実運用でその性能を達成したという意味ではありません。どの工程の品質が後続の結果に影響するかを調べられることに意味があります。

診断全体の成否だけを見ていると、失敗の理由は分かりません。中間成果物を評価できれば、改善すべき場所を絞り込めます。

MetaVulが示す、評価から改善へのつながり

MetaVulは、評価結果を使って脆弱性検知のハーネスを改善する研究です。改善役のエージェントが過去の診断結果や正解を参照してハーネスを変更し、診断役が変更後のハーネスで再び評価を受けます。

評価方法にも考えさせられます。脆弱な関数を「脆弱」と判定するだけでは足りません。修正済みの関数を「安全」と区別できて初めて、そのペアを正解とします。何でも脆弱だと答える方法では、高い評価を得られない設計です。

ただし、ある指標が改善すれば診断品質のすべてが向上するわけではありません。論文では、誤検知の減少と引き換えに、見逃しが増える場合も示されています。評価指標の選び方は、どのようなハーネスを良いと判断するかに直結します。

MetaVulの対象は、C/C++の関数単位のソースコード診断です。ブラックボックス型診断に同じ改善効果が出ると示した研究ではありません。それでも、評価結果を残し、ハーネスを変更し、別の対象で確かめるという改善の構造は参考になります。

評価のための環境を持てるか

見逃しを測るには、脆弱性が存在すると分かっている対象が要ります。診断サービスを継続的に改善するなら、まず脆弱性を埋め込んだ基準となる検証環境を持つことが、現実的な出発点だと思います。

公開された演習環境も有用です。一方で、課題や解法がモデルの学習データに含まれている可能性は考慮しなければなりません。評価の信頼性を高めるには、内容を管理でき、診断過程も追跡できる環境が必要です。

そこで同じ診断を複数回行い、収集した情報、選んだ検査、実行した内容、結論の根拠を比較する。見逃しや誤検知に加えて、各工程にかかった時間やコストも記録する。そうして初めて、ハーネスの変更によって何が良くなり、何が悪くなったのかを判断できます。

最初からすべての技術や脆弱性を網羅することはできません。基準となる環境を作り、新しい脆弱性や診断対象に合わせて更新していく必要があります。

継続的な改善基盤が競争力になる

同じモデルを利用できても、同じ診断品質になるとは限りません。どの情報を集めるか、どの検査を選ぶか、結果をどう解釈するかは、ハーネスの設計に左右されます。そして、その設計を改善するには、良し悪しを判断できる評価基盤が要ります。

評価対象を整え、複数回の実行を記録し、失敗した工程を特定する。改善案を試したら、既知の課題だけでなく別の対象でも確かめる。発見率だけでなく、見逃し、誤検知、品質の揺らぎ、時間、コストの変化を見る。

これは簡単には作れません。評価環境の更新には手間がかかり、何を正解とするかにも判断が要ります。改善案をどこまで自動で採用するかも、品質や安全性を踏まえて設計すべき論点として残ります。

攻撃側もAIを使って試行を速めていくとすれば、防御側は、品質・安全性・性能・コストを確かめながら改善を続ける必要があります。モデルやプロンプトを選ぶだけでなく、変化に合わせて診断方法を更新できることが重要になります。

私が競争優位性になると考えているのは、特定のモデルを使うことではありません。診断がどこで失敗したかを説明でき、その結果を次のハーネス改善につなげられる基盤を持つことです。

おわりに：診断を改善できる形で測る

AIによる脆弱性診断には、まだ難しい問題が多くあります。長い診断工程の結果が揺れるとき、その原因をどう切り分け、再現可能な形で評価するかも、その一つです。

PentestEvalは、診断を工程ごとに測る視点を与えてくれます。MetaVulは、評価をハーネスの改善につなぐ方法を示しています。二つの研究の対象は異なりますが、どちらも「診断の品質をどう捉え、次の改善に変えるか」という問いにつながっています。

発見できた件数だけでは、次に何を直すべきかは分かりません。何を見て、何を試し、どこで見逃したのか。その過程を評価し続けられる基盤を作り、育てられるかどうかが、これからのAI脆弱性診断サービスの質を分けると考えています。
